## Sender comparison and remaining boundary

The current Rust `keyboard_batch::character` and Python `win32.type_unicode` both build `KEYEVENTF_UNICODE` pairs with `wVk=0`, one key down and one key up per UTF-16 unit, then pause 12 ms after each character. [Microsoft documents](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-keybdinput) the `VK_PACKET` message route into `WM_CHAR`; a successful `SendInput` submission still does not prove that Notepad consumed the resulting character. The guard passes injected events through. Its reserved-key probe ran during the exact direct control, but probe interaction during app delivery was not recorded in this run.

The direct control has no preceding dictation hotkey or inference work and performs only the harness's pre/post checks plus its pre-send real-input guard. Murmur first waits for physical modifiers to release, then verifies the selected top-level window before **each** character; it does not verify editor focus per character. Native phases observed no held modifiers before the app delivery wait, no real user input occurred, and the editor was focused at sampled times. These samples do not show the key state or editor focus at every app `SendInput`. The prior F13 run at `d45646f` did prove a separate held-modifier refusal/recovery path; H1/I1/I4/I5 remained failing there.

No production correction is justified by these artifacts. In particular, increasing the pause, synthesizing modifier releases, suppressing the guard probe, sending Escape, or refocusing Notepad would pick an unproved cause or hide the required Alt-menu behavior.
